| Q27 | Distribution | (owner, final, 2026-10-26) Portable zips only, 6 of them: Windows, Linux, macOS, each on x64 and arm64. Self-contained (no runtime install). Single file if that proves best; otherwise a plain program folder, but everything sits in the zip root (zip > files, not zip > folder > files). Names: `G3MStudio-<OS>-<ARCH>-<VERSION>.zip`. | Q28 | Updates | (owner, final) G3MStudio watches the owner's GitHub releases. If the highest available version is above the running one, it downloads the right zip for the user's OS and architecture; the user clicks Restart to Update; the app saves, then an external updater closes it, extracts all files into the folder of the previous executable, replaces them and starts the new one; the user returns to almost the same state. Highest of release, pre-release (optional channel in settings) and the running version wins. No code signing and no signature scheme (supersedes OI-010); the trust root is the owner's GitHub account. All user data lives in the per-user app data folder (for example `%LOCALAPPDATA%/G3MStudio` on Windows), never in the program folder. Autosave is required. |
| Q29 | Crash reporting | (owner, final) Sentry integration, opt-out, can be switched off during onboarding and later in settings. Keys come from GitHub secrets and are added to releases by CI only. | Q30 | G3MTool and G3M changes | (owner, 2026-10-26) Cancel support for long operations in G3MTool is welcome (cancel patching and similar) because it is useful and small. Otherwise no new features. Global rule: every change adds as few lines of new code as possible. |
| Q31 | Workspace model | (owner direction, 2026-10-26; details in decisions/0010-workspace-and-sync.md) A data file is the workspace. (Superseded by Q36: Direct mode is the default and the project is opt-in.) A project is an export of everything in a `.yyp`-like layout in the user data folder (location customizable). Direct mode works on the data file as UndertaleModTool does, with no project. Project and data file are separate things connected only by sync, which is atomic and fast. Auto sync on save is a setting; a Sync button is always available; external changes to the data file ask what to do. A project can recreate a lost or broken data file. Advanced feature: create a new data file from scratch. |
| Q32 | Sentry details | (owner, 2026-10-26) Opt-out with scrubbing: no IP, no user name, paths reduced to relative or hashed parts, no data file content, no breadcrumbs with file names. Onboarding shows a clear notice and a switch before any report can be sent; also a setting. |

| Q34 | Live model | (owner) Memory is the live model; every edit goes to a crash-safe journal; Sync writes the data file from memory. How Direct and Project mode are offered is still being decided (ADR-0010). |

| Q36 | Modes and history | (owner, 2026-10-26) Direct mode with a safety net (journal plus 1 to 3 rotating backups) is the default; the project is an opt-in layer enabled by an always-visible action. | Q37 | G3MLib 1.1.0 `.yy` interop | (owner, 2026-10-26) All five types in 1.1.0: sprite, sound, script, object, room (OI-052 option 1 widened). | Q38 | macOS and the updater | (owner) macOS ships `G3MStudio.app` at the zip root. Implementation note: a running program cannot overwrite its own executable on Windows, so the app starts a temporary copy of itself in a hidden update mode (same code, no second product), which performs the swap and relaunches; on failure it restores the backups. |

| Q42 | No bundled scripts | (owner, 2026-10-26) G3MStudio ships no bundled scripts such as ExportAllSounds.csx. | Q43 | Updater mechanism | (owner, 2026-10-26) Supersedes the "temporary copy of itself" in Q38: the update runs through a small native script that the app writes and launches (a `.bat` or `.cmd` on Windows, `sh` on macOS and Linux, whatever is guaranteed on that OS), then exits.
