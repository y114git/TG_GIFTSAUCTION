# Reviewing the real window without computer use

Status: working method, 2026-11-02. Computer use cannot list G3MStudio (Q65), but the built app can still be driven and photographed from PowerShell, with no focus and no keystrokes.

1. Start the Release build with a data file: `G3MStudio.exe "<path>\data.win"`.
2. Make the script DPI aware (`SetProcessDPIAware`) before reading the window rectangle, or the capture is cut off at 125% scaling.
3. Click with `PostMessage` to the main window handle: `WM_MOUSEMOVE` (0x200), then `WM_LBUTTONDOWN` (0x201) and `WM_LBUTTONUP` (0x202), the position in client pixels (window pixels minus the client offset from `ClientToScreen`). Avalonia reacts without the window being in front.
4. Take the picture with `PrintWindow(hwnd, dc, 2)` into a `Bitmap` and read the PNG.

What does not work: keystrokes (`SendKeys`, `keybd_event`) need the window in front, and Windows refuses the foreground to a background tool, so shortcuts and typing cannot be tested this way. Menus and flyouts are separate windows and are missing from the picture (the menu title shows as pressed). The explorer restores its last layout, so row positions differ between runs: take a picture before clicking.

Found with it: shader tabs wrapped to two rows and the editor touched the property filter (fixed). Everything else photographed (sprite, tile set, shader, object tabs, the Game group with Tags, Feature Flags and Language) matched the headless renders.

2026-11-03 check: the Debug build started on the smallest corpus file (Five Nights at Frickbear's 3, 76,009 resources) restored its shader tab and the Explorer, Inspector, History and Output docks in a real window and the layout matched the headless renders. The tabs added since (sound reference line, variable counters, runtime choice) were not reached: scrolling the 76,000 row Explorer with posted wheel messages is too slow, and menus and dialogs are separate windows that PrintWindow does not see. They stay reviewed in headless frames only (Q65).

2026-11-03 second check: a tiny sample data file (4 objects, 5 scripts, 1 room, written by the test data helper) is small enough to drive by posted clicks. With it the real window showed the Game Options tab with the shader extension rows, a script tab, the object list, the room tab with its toolbar and Inspector, a tab drag (`scr_0` moved in front of `Game Options`) and tab overflow (a scroll arrow and the selected tab kept in view). The drag needs a script that posts WM_MOUSEMOVE with the button flag set between the press and the release; 12 steps of 60 ms worked.

2026-11-03 third check: a sample written with ResourceListCommand (sound, path, shader, timeline, objects, scripts, room; no sprite because it needs a texture page, no font, sequence, curve or particle system because those are made from templates) opened in the real window. The sound tab (Play button, wav info, the new audio entry line, flags and properties), the path tab (Move all fields and canvas), the shader tab (four GLSL and HLSL views with highlighted text) and the timeline tab (Add moment) drew correctly with no clipped or overlapping controls. Not reached in a real window: sprite, font, sequence, curve, particle and tile set editors, and every menu and dialog.

2026-11-03 fourth check, on the 76,009 row corpus game: the Explorer scroll bar thumb can be dragged with the drag script (press, 12 mouse moves with the button flag, release) to reach the top, and a click on a group's triangle collapses it, so the later groups come into view without hundreds of wheel messages. In that game the real window showed the sprite tab (three frames with their sizes, Play, Lock origin, properties), the tile set tab (size line, tile list, Find rooms using this tile, properties; its Texture row has no value box and the tile list is text only, which may be this tile set having no texture, not checked) and the object tab (events list with Remove, the event type box with Add event, physics vertex boxes, properties with the sprite reference). No clipped or overlapping controls. The game has no fonts, sequences, curves or particle systems, so those editors, the room view with content, and every menu and dialog are still not seen in a real window.

2026-11-03 fifth check (Pizza Tower, real window and the headless picture harness, G3MSTUDIO_SHOTS with G3MSTUDIO_CORPUS_DIR): every room tab with elements showed a blank band under the canvas. Cause: RoomElementList derives from ListBox without a StyleKeyOverride, so it found no control theme, had no template and drew no rows (the probe found 1385 items, no ScrollViewer and no realized row). Fixed by returning typeof(ListBox) as the style key, with a test that the list holds a ScrollViewer, and the picture of the room tab now lists its instances. The real window also showed the room view with content (layers, tiles, Inspector), and the picture harness showed the font, audio editor, pixel painter and onboarding windows without clipped or overlapping controls.

Finding: every menu showed the editor text through it because Bg.Overlay was 90% opaque; it is now opaque (OI-309) and the menu picture reads clean. A fold marker of the code editor still shows over the menu in the headless picture only (draw order inside the headless renderer, not seen with real popups).
